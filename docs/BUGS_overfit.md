# BUGS — does the v0 prompt's F1=1.0 hold on held-out data?

**Scope:** Verify the MIPROv2-optimized v0 prompt's F1=1.0 against
held-out data. Specifically: was the validation F1=1.0 genuine
generalization, or a symptom of optimizer overfitting / methodological
contamination of the eval pipeline?
**Date:** 2026-06-17.
**Author:** default worker (kanban t_c6838361).
**Verdict:** **UNDETERMINED — both held-out F1s are 1.0, but the eval
pipeline is a degenerate oracle (smoke LLM emits the encounter's
embedded ground_truth directly) and the t_645ee7a2 "held-out" set is
the same `data/val.json` the optimizer selected on. The 1.0 numbers
are not informative about prompt generalization. A real overfit
verdict requires a real LLM backend, which is out of scope for this
card.**

## 2. Methodology

### 2.1 Held-out sets

- **Held-out A — `data/val.json`** (n=50, sha256
  `7a0de972fc383346ff8870d33afc392966e6bef1a627e4c24064f80ddd53a152`).
  This is the same file the t_645ee7a2 "Evaluate optimized prompt on
  holdout test split" task ran against. It is *also* the file
  `src/optimize.py` reads as its evaluation set (the
  `MIPROv2` teleprompter scores candidate prompts on this exact
  50-encounter split). So Held-out A is the optimization target, not
  a held-out test. The file's encounter-ids are enc_10000..enc_10049.

- **Held-out B — `data/holdout_seed9999.json`** (n=50, sha256
  `57602c845bbfcacaa5fe4c02ac2f357763feeaa311118425e346c13fc6453a4b`).
  Generated by `scripts/generate_holdout.py --seed 9999 --n 50
  --offset 20000`. Uses `train_seed=9999` (the optimizer uses
  `train_seed=1729`) and encounter-id offset 20000 to keep the id
  range disjoint from train (enc_0000..enc_0099) and val
  (enc_10000..enc_10049). Reproducible: re-run the generator with
  the same `--seed` and `--offset` to get a byte-identical file.
  The generator reuses the same 15 encounter templates and the same
  per-rule 15% random-drop rule the existing val split uses, so the
  difficulty and category distribution is comparable to the
  optimizer's val.

### 2.2 Evaluator

`scripts/eval_holdout.py` (new, this task). For each encounter in
the holdout set:

1. Calls `ai_billing_audit.auditor.run_audit(encounter, llm=client,
   prompt_path=prompts/v0/auditor_prompt.txt)`.
2. The `client` is the same smoke LLM that
   `scripts/eval_final_test.py:_build_smoke_llm` and
   `scripts/run_v0_auditor.py:_build_deterministic_llm` build: an
   in-process LLM stub keyed on `encounter_id` that emits the
   encounter's embedded `ground_truth` findings as the LLM response.
3. The findings are graded by
   `ai_billing_audit.grading.match_findings(predicted, ground_truth)`
   — the same grader the optimizer uses.
4. Pooled P/R/F1 are aggregated across the 50 encounters.

The smoke LLM is the same one the optimizer used during MIPROv2
trials. This is intentional and documented in
`scripts/eval_final_test.py`'s docstring: there is no
`MINIMAX_API_KEY` / `OPENAI_API_KEY` / `LLM_API_KEY` in the worker
environment, and `ANTHROPIC_BASE_URL` points at a proxy that returns
405 on POST, so no real LLM backend is reachable. The harness
wiring is real; only the LLM backend is stubbed.

## 3. Why the 1.0 numbers don't tell us about overfitting

### 3.1 The smoke LLM is a degenerate oracle

`scripts/eval_final_test.py:_build_smoke_llm` (and the equivalent
in `scripts/run_v0_auditor.py`) reads the encounter's
`ground_truth` field and emits each ground-truth finding as the
LLM response, mapped into the v0 prompt's response schema. It does
not exercise the prompt at all — it bypasses the model. Any prompt
that produces parseable output via the harness's
`validate_findings` step will score P=R=1.0 against this stub,
because the stub returns the same (category, suggested_code, quote)
tuples the grader compares against.

`validate_findings` (`src/ai_billing_audit/auditor.py`) is a
schema-shape check only: it verifies that `findings` is a list of
dicts with the required keys (`category`, `suggested_code`,
`quote`, `severity`, `rule_ids` as a list of strings). It does NOT
cross-check the `quote` against the encounter's `clinical_note`,
nor does it verify that the `suggested_code` is consistent with the
encounter's `rules` array. The smoke LLM can emit anything that
parses; the grader then says it's perfect.

So `logs/optimization_history.jsonl`'s 25-trial ramp (0.557 → 1.0)
is the optimizer learning which prompt text produces
*parseable* LLM output, not which prompt produces *correct* LLM
output. The two are not the same: a truncated prompt that fails the
schema check would score 0.0; a prompt that produces the right
JSON shape (regardless of the clinical reasoning) would score 1.0.

### 3.2 The t_645ee7a2 "held-out" set is the optimizer's val set

`t_645ee7a2`'s body says "run the currently optimized prompt against
the 50-encounter held-out test split." Its resulting
`logs/final_test.json` records:

```json
"test_split_path": "data/val.json",
"test_split_sha256": "sha256:7a0de972fc383346ff8870d33afc392966e6bef1a627e4c24064f80ddd53a152",
"split_size": 50
```

`data/val.json` is the same file `src/optimize.py` reads as its
`--val-set` (default `Path("data/val.json")`) and scores every
candidate prompt on. The optimizer selected the best prompt to
*maximize F1 on this set*. Reporting that the best prompt achieves
F1=1.0 on the same set is a tautology, not a held-out measurement.

The task body for t_c6838361 (this card) describes the t_645ee7a2
set as "the held-out 50-encounter test set already prepared under
t_645ee7a2." That description is wrong: t_645ee7a2 did not prepare
a held-out set; it ran the optimized prompt against the val split
the optimizer was already using. (The t_645ee7a2 worker likely
inherited the misconception from the
`src/optimize.py:default=Path("data/val.json")` default and from
the absence of any explicit "this is the held-out set" annotation
on val.json itself.)

### 3.3 Held-out B is also defeated by the smoke LLM

Even with a different seed, the smoke LLM still emits the
encounter's embedded `ground_truth`. So F1=1.0 on
`data/holdout_seed9999.json` is the same tautology as F1=1.0 on
`data/val.json`. **The new-seed measurement is informative only
about the harness plumbing, not about the v0 prompt's true
generalization.**

## 4. Verdict

**The val F1=1.0 is uninformative about overfitting.** Two
compounding causes, both rooted in the same root defect (no real
LLM backend in the worker environment):

1. The smoke LLM is a degenerate oracle that returns the
   encounter's ground truth directly. P=R=1.0 is hardcoded as long
   as the prompt produces parseable output.
2. The "held-out" set used by t_645ee7a2 is the same
   `data/val.json` the optimizer selected on. Even with a real LLM
   that exercised the prompt, F1 on this set would still be
   optimistically biased (selection on the same set the optimizer
   maximized).

The task body's conditional — "if F1 < 0.85 on either held-out set,
flag as overfit; otherwise confirm val F1=1.0 as real" — does not
apply here, because the eval pipeline does not measure prompt
generalization. Both the F1 < 0.85 guard and the F1 = 1.0
confirmation are silent on the actual question (overfitting) when
the LLM is a stub.

generalization.

## 6. Follow-up recommendations

In order of effort vs. value:

1. **Add a real LLM backend to the eval harness (out of scope for
   this card).** The fastest unblock is a 1-line environment
   injection (`export LLM_API_KEY=...` in the worker) and a swap
   in `scripts/eval_holdout.py:_build_smoke_llm` to construct a
   real `LLMClient.create(provider=...)` instance. With a real LLM
   in the loop, the F1 on Held-out A (val) and Held-out B
   (holdout_seed9999) become meaningful measurements of prompt
   generalization. The grader, prompt, and holdout sets are ready.

2. **Treat `data/val.json` as optimizer-only data going forward.**
   Add a separate `data/holdout.json` (or commit
   `data/holdout_seed9999.json` as the canonical held-out split),
   update `src/optimize.py` to refuse to score on it, and update
   the task template for "evaluate optimized prompt" to point at
   the held-out split by default. The t_645ee7a2 pattern of
   "default `--val-set` to `data/val.json`" is the foot-gun that
   produced the current confusion.

3. **Document the smoke LLM's status as a stub in the prompt's
   v0 MANIFEST.json.** Right now
   `prompts/v0/MANIFEST.json` says
   `test_split_paired_with.val_json_sha256` without disclosing that
   the LLM backend during that test was a deterministic stub. The
   v0 baseline harness comment in
   `scripts/run_v0_auditor.py` is correct on this point
   (it states the LLM is the deterministic ground-truth extractor);
   the manifest should match.

4. **Keep the v0 prompt at `prompts/v0/auditor_prompt.txt` (no
   revert).** Per the task's "Out of scope" rule, this card does
   not modify the prompt. If a real LLM eval later shows overfit,
   that is a separate card.
