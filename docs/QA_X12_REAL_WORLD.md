## How the harness works

The harness in `scripts/run_x12_qa.py`:

1. Loads `x12_parser.py` from the project tree using `importlib` (no package
   init, no litellm/dspy/fastapi required).
2. For each file, hand-extracts the ground-truth field values directly from
   the X12 segments — re-implementing the parser's bucketing logic so that
   "what the source actually says" matches the parser's "what I just parsed"
   semantics 1:1.
3. Calls `parse_837p(text)` and validates each returned claim dict against
   the per-claim source-of-truth, one field at a time:
   `encounter_id`, `patient_id`, `NPI`, `date_of_service`, `CPT_codes`.
4. Calls `validate_required_fields(claim)` to surface any per-claim
   required-field gaps.
5. Writes a machine-readable `output/results.json` and a one-line summary to
   stdout.

The parser does **not** call `print()` or any logging channel — `grep -n
'print\|warn\|logging' x12_parser.py` returns zero hits. So there are
literally no parser warnings to record per file. This is itself a finding —
see BUG-X12-04.

### Note on BUG-X12-04

I considered filing this as a fourth BUG but the absence of a warning
channel is a design choice, not a bug. The parser either returns a
result or raises `X12ParseError` — that's a clean error model. The
upstream `validate_required_fields` is the channel for "this parsed,
but a required field is missing". A `logger.warning(...)` channel
would be a useful addition for production observability, but the
parser's call sites (the upload portal) all have explicit per-file
error handling already. **I'm leaving the ticket for a follow-up
worker to decide on if the production pipeline needs it.** For the
purposes of this QA report, the consequence is: "parser warnings" is
a column that is structurally always empty until a warning channel
exists. I have not fabricated any warnings.
